## 一、系统概述

### 1.1 定位与目标

知识库构建系统是整个「指令泛化 Agent」项目的 **核心处理引擎**。它接收 GUI 采集系统产出的原始交互树 JSON，经过三级处理流水线，最终产出可用于语音助手意图识别的结构化知识库。

> **数据流：GUI 树 JSON → 扁平化 KB → LLM 增强 → 结构化 KB → 泛化增强 → 最终产出**

### 1.2 为什么需要多级处理

原始 GUI 树是嵌套的树形结构，直接使用存在以下问题：

| 问题 | 说明 |
|------|------|
| 结构复杂 | 树深 3-8 层，嵌套 JSON 难以直接检索 |
| 缺少语义 | 原始节点只有界面描述，没有自然语言指令 |
| 无意图分类 | 节点散乱，没有按用户意图归类 |
| 表述单一 | 缺少多样化的指令表述，无法覆盖真实用户的说法 |

因此设计了**三级流水线**，逐步解决这些问题：

```
Level 1: 扁平化          Level 2: 结构化           Level 3: 泛化增强
┌──────────────┐     ┌──────────────────┐     ┌──────────────────┐
│ GUI 树 JSON  │────▶│ 扁平化 KB        │────▶│ 结构化 KB        │
│ (嵌套树结构) │     │ (平铺条目列表)   │     │ (意图分类+统计)  │
│              │     │ + LLM 生成指令   │     │                  │
└──────────────┘     └──────────────────┘     └────────┬─────────┘
                                                       │
                                              ┌────────▼─────────┐
                                              │ 泛化增强结果      │
                                              │ (6种类型×N条变体) │
                                              └──────────────────┘
```

## 三、核心模块详解

### 3.1 Level 1：扁平化知识库构建

#### `tree_parser.py` — GUI 树解析器（100行）

**设计目标：** 将嵌套的 GUI 树 JSON 转化为扁平的条目列表。

**核心算法：递归 DFS 遍历**

```python
def _walk_node(node, path, entries):
    # 1. 提取当前节点名称、类型、描述
    # 2. 维护路径链 (path + [name])
    # 3. 如果有 actions → 为每个 action 生成一条 entry
    # 4. 如果是叶子节点无 action → 记录为 view 类型
    # 5. 递归处理 children
```

**为什么要扁平化？**

| 树形结构 | 扁平化结构 |
|---------|-----------|
| 嵌套 JSON，查找需递归 | 平铺列表，O(1) 遍历 |
| 路径信息隐含在层级中 | `path_str` 显式记录完整路径 |
| 难以做批量 LLM 增强 | 逐条送入 LLM，天然并行 |
| 不便检索 | 可直接接入 BM25/向量检索 |

**去重策略：** 基于 `(node_name, action_type, path_str)` 三元组去重。同一节点在不同路径下被多次采集时，保留唯一实例。

#### `llm_enhancer.py` — LLM 增强器（98行）

**设计目标：** 为每个 GUI 操作节点生成用户可能说出的自然语言指令。

**为什么需要 LLM 增强？**

原始 GUI 节点只有结构化的界面信息（如"搜索框"、"点击"、"闹钟时钟 > 时钟Tab > 搜索框"），但语音助手需要理解用户的自然语言（如"帮我在闹钟里搜一下"、"打开时钟的搜索功能"）。

LLM 增强为每个节点生成两类信息：
1. **`generated_queries`**（5-8条）：用户可能的口语化指令
2. **`intent_keywords`**（3-5个）：意图关键词，用于检索匹配

**增强 Prompt 设计要点：**
- 明确给出节点的完整上下文（名称、类型、路径、描述）
- 要求口语化、多样化的表述
- 严格的 JSON 输出格式约束
- 温度设为 0.7，平衡多样性与准确性

**容错机制：**
- 最多重试 3 次
- 指数退避（2^attempt 秒）
- 失败时填充空列表，不阻塞整体流程
- 每条请求间隔 0.3 秒限流

#### `build_kb_parallel.py` — 并行 KB 构建入口（105行）

**设计目标：** 批量处理 47 个 App 的知识库构建。

**关键设计决策：**

1. **为什么最终用串行而非并行？**

   虽然文件名包含 "parallel"，但实际采用串行执行：
   ```python
   # 串行执行（LLM API 有限流，并行反而慢）
   for task in tasks:
       result = build_single_app(task)
   ```
   原因是 模型服务网关 有 QPS 限制，多进程并行会触发限流导致大量重试，反而更慢。保留了 `Pool` 的代码结构以便未来 API 扩容后切换。

2. **断点续跑机制：**
   ```python
   if os.path.exists(output_path):
       data = json.load(open(output_path))
       enhanced = sum(1 for e in data if e.get('generated_queries'))
       if enhanced == len(data) and len(data) > 0:
           return app_name, len(data), enhanced, 'skipped'
   ```
   检查已有文件中所有条目是否都已增强完成，是则跳过。这意味着中途中断后重新运行，只需处理未完成的 App。

3. **文件名清洗：** `basename.replace('(1)', '')` 处理 Windows 下载时自动添加的序号后缀。

### 3.2 Level 2：结构化知识库构建

#### `build_kb_structured_auto.py` — 自动结构化 KB（197行）

**设计目标：** 利用 LLM 将散乱的操作节点按用户意图分类，生成结构化的知识库。

**为什么需要意图分类？**

扁平化 KB 中的条目是无序的操作节点列表。但在语音助手场景中，用户的指令总是带有某种**意图**（如"设置闹钟"、"查看天气"、"拍照"）。意图分类将节点按用户目标归组，使得：
1. 检索时可以先匹配意图，再定位具体节点
2. 结构化展示更直观（按意图分组而非按页面层级）
3. 便于统计和评估每个意图的覆盖度

**LLM 意图分类 Prompt 设计：**

| 约束 | 原因 |
|------|------|
| 6-10 个意图 | 太少则粒度粗，太多则碎片化 |
| 意图名 2-6 字 | 简洁便于展示和检索 |
| 每个节点必须且仅归入一个意图 | 避免分类歧义 |
| 尽量均衡分配 | 防止出现"其他"这样的垃圾桶意图 |

**双向回写机制：**

这是一个重要的设计决策——结构化完成后，会将 `intent_name` **回写**到扁平化 KB 中：

```python
# 给每个节点附加意图名称
for e in entries:
    if e['node_name'] in nodes:
        e['intent_name'] = intent['意图名称']

# 回写 intent_name 到 flat kb
with open(kb_path, 'w', encoding='utf-8') as f:
    json.dump(entries, f, ensure_ascii=False, indent=2)
```

这样扁平化 KB 和结构化 KB 的意图信息保持一致，下游无论使用哪个版本都能获取意图标签。

**断点续跑：** 已有 ≥6 个意图的结构化文件会跳过，避免重复调用 LLM。

### 3.3 Level 3：指令泛化增强

#### `pipeline_v3.py` — 泛化增强主管线（194行）

**设计目标：** 对知识库中每条操作节点，生成多种风格的自然语言指令变体。

**为什么需要泛化增强？**

LLM 增强器（Level 1）已经为每个节点生成了 5-8 条指令，但这些指令风格相对单一。真实用户的表述千差万别：

- 有人说"帮我设个明天早上7点的闹钟"（清晰）
- 有人说"定个闹铃"（模糊）
- 有人说"帮我订个闹中"（错别字）
- 有人说"先打开闹钟，然后设一个7点的提醒，最后关掉震动"（多步依赖）
- 有人说"用闹钟定个提醒，然后发微信告诉老婆"（跨应用）

**6 种泛化类型的设计逻辑：**

| 类型 | 数量 | 目标 | 典型示例 |
|------|------|------|---------|
| `clear` | 4条 | 标准无歧义指令 | "打开闹钟应用的添加闹钟功能" |
| `parallel` | 4条 | 同义替换多样化 | "新建一个闹铃" / "创建提醒" |
| `fuzzy` | 3条 | 口语化简短表述 | "定个闹钟" / "加个铃" |
| `robust` | 3条 | 含噪声的真实表述 | "帮我订个闹中" / "搞个那啥提醒" |
| `dependency` | 2条 | 多步骤复合指令 | "先打开闹钟再设置7点提醒" |
| `cross_app` | 2条 | 跨应用联合指令 | "用闹钟定个提醒然后发微信通知" |
| **合计** | **18条** | — | — |

**为什么是这个配比？**

```
clear(4) + parallel(4) = 8条基础指令 → 保证召回基本盘
fuzzy(3) + robust(3) = 6条噪声指令  → 提升真实场景鲁棒性
dependency(2) + cross_app(2) = 4条   → 覆盖复杂交互场景
```

基础指令占比最高（44%），确保常见表述被覆盖；噪声指令占 33%，模拟真��用户的不规范输入；复杂指令占 22%，覆盖高级场景但不过度膨胀数据。

**断点续传设计：**

```python
results = {}
if resume and os.path.exists(output_path):
    results = json.load(...)  # 恢复已有进度

for i, entry in enumerate(entries):
    key = entry.get('path_str', f'entry_{i}')
    if key in results:  # 跳过已处理条目
        continue
    # ... 处理逻辑
    if (i + 1) % 10 == 0:  # 每 10 条保存一次
        json.dump(results, ...)
```

以 `path_str` 作为唯一键，确保重启后精确恢复到断点位置。每 10 条保存一次，最多丢失 9 条的工作量。

## 六、全局配置 (`config.py`)

### 6.1 路径配置

```python
BASE_DIR    = 项目根目录
DATA_DIR    = data/
GUI_JSON_DIR = data/gui_json/       # 原始 GUI 树
KB_FLAT_DIR  = data/kb_flat/        # 扁平化 KB
KB_STRUCT_DIR = data/kb_structured/ # 结构化 KB
```

### 6.2 LLM API 配置

| 配置项 | 值 | 用途 |
|--------|-----|------|
| DOMAIN | 由部署环境配置 | 模型服务网关 |
| LLM_MODEL | Doubao-Seed-2.0-pro | 文本增强模型 |
| 认证方式 | HMAC-SHA256 签名 | AI Gateway 安全协议 |

**为什么用两个不同模型？**

- **采集阶段**（Gemini-3.1-pro）：需要多模态能力分析截图，Gemini 视觉理解能力强
- **增强/分类阶段**（Doubao-Seed-2.0-pro）：纯文本任务，Doubao 中文能力好、性价比高

### 6.3 API 调用封装

`config.py` 提供两个全局调用函数：
- `call_llm(prompt)` — 返回纯文本内容
- `call_llm_json(prompt)` — 返回解析后的 JSON 对象（自动清理 markdown 包裹）

两者均内置重试机制（3次）和指数退避。

## 七、设计决策与权衡

### 7.1 为什么分三级而非一步到位？

| 方案 | 优点 | 缺点 |
|------|------|------|
| 一步到位 | 流程简单 | 中间结果不可复用，调试困难 |
| **三级流水线** | 每级独立可调，中间产物可复用 | 流程较长 |

三级设计带来的核心优势：
1. **独立调试**：解析出问题不影响增强，增强出问题不影响结构化
2. **增量更新**：新增 App 只需从 Level 1 开始，已有 App 的 Level 2/3 不受影响
3. **中间产物复用**：扁平化 KB 可直接用于检索；结构化 KB 可直接用于展示

### 7.2 为什么 LLM 增强放在扁平化阶段而非结构化阶段？

先增强再分类，而非先分类再增强：
1. 增强只需要节点本身的信息，不依赖意图分类
2. 意图分类可以参考已有的 `generated_queries` 来更准确地归类
3. 分离后可以独立重跑增强而不影响分类结果

### 7.3 为什么断点续传用文件而非数据库？

| 方案 | 优点 | 缺点 |
|------|------|------|
| SQLite | 事务安全，并发友好 | 多一个依赖，查看不直观 |
| **JSON 文件** | 零依赖，可直接查看编辑 | 并发写入不安全 |

考虑到：
1. 47 个 App 串行处理，不存在并发写入
2. JSON 文件可以直接用文本编辑器查看和手动修复
3. 减少外部依赖

### 7.4 泛化增强的温度设置

| 阶段 | 温度 | 原因 |
|------|------|------|
| 意图分类 | 0.3 | 需要稳定、一致的分类结果 |
| 指令增强 | 0.7 | 需要多样性，同时保持语义正确 |
| 泛化增强 | 0.7 | 平衡创造性与可靠性 |

## 八、已知限制与改进方向

### 8.1 当前限制

1. **LLM 调用成本**：全量处理 47 个 App 需要数千次 LLM 调用，约耗时 4-6 小时
2. **意图分类质量**：LLM 的意图分类偶有不合理之处（如将无关节点归入同一意图）
3. **文本截断**：节点文本超过 12000 字符时会被截断，可能丢失信息
4. **泛化质量不均**：`robust` 和 `cross_app` 类型的生成质量相对不稳定
5. **无人工审核环节**：除红色数据修复外，缺少系统化的质量把关机制

### 8.2 改进方向

1. **缓存层**：引入 embedding 缓存，相似节点的增强结果可复用
2. **批量 API**：利用 LLM 的 batch API 降低成本
3. **意图分类优化**：采用两阶段分类（先粗分再细分），提高准确率
4. **质量评估**：引入自动化质量评分（如指令与节点的语义相似度）
5. **向量检索**：从 BM25 升级到向量检索，提升语义匹配能力
