## 一、系统概述

### 1.1 定位与目标

GUI 采集系统是整个「指令泛化 Agent」项目的 **数据源头**。它的核心任务是：

> **通过 ADB 连接真实 vivo 手机，逐页截图 + 调用多模态大模型（Gemini）解析，自动构建每个 App 的完整 GUI 交互树。**

最终产出：47 个 App 的 GUI 交互树 JSON 文件（存放于 `data/gui_json/`），作为下游知识库构建的原始输入。

### 1.2 为什么需要这个系统

| 问题 | 传统方案 | 本系统方案 |
|------|---------|-----------|
| App 界面元素获取 | 手工整理 / XML dump | **截图 + 多模态 LLM 自动识别** |
| 深层页面发现 | 仅首屏 | **DFS 递归探索，逐层深入** |
| 交互语义理解 | 仅标签名 | **LLM 理解功能含义、预期变化** |
| 数据持久化 | 无断点 | **实时保存 JSON，支持断点续跑** |

传统的 UI 自动化测试工具（如 UIAutomator）只能获取 XML 布局结构，缺乏语义理解能力。本系统借助多模态大模型，不仅能识别界面元素，还能理解每个元素的**功能含义**和**交互预期**，这对于下游生成自然语言操作指令至关重要。

## 三、核心文件说明

### 3.1 `agent_persistent.py` — 采集主程序（343行）

这是采集系统的核心入口，实现了一个**人机协作的半自动 DFS 爬虫**。

**设计思路：为什么是半自动而非全自动？**

全自动采集面临以下难题：
1. **页面导航不可逆**：某些页面进入后无法通过简单返回回到上一级
2. **弹窗/权限拦截**：系统弹窗、权限申请等需要人工判断
3. **动态内容干扰**：信息流、广告等动态内容会影响自动化判断
4. **探索深度控制**：部分子页面不值得深入（如纯展示页）

因此采用 **DFS 自动调度 + 人工确认** 的混合模式，兼顾效率与准确性。

**关键函数：**

| 函数 | 作用 | 设计考量 |
|------|------|---------|
| `load_tree()` / `save_tree()` | JSON 树持久化 | 每次操作后立即保存，防崩溃丢失 |
| `find_next_node()` | DFS 寻找下一个未探索节点 | 通过 `_explored` 标记避免重复 |
| `process_new_components()` | 为新节点补充 UUID 和状态 | 保证树结构一致性 |
| `clean_llm_json()` | 清理 LLM 返回的 markdown 包裹 | LLM 常不遵守"不要代码块"的指令 |

**两种采集模式：**

```
用户输入:
  s → 单屏构建：截一张图，LLM 解析当前页面所有元素
  m → 多屏构建：连续截多张图（滚动页面），增量追加去重
  n → 跳过此节点（标记为不需探索）
  q → 退出保存
```

**单屏模式 vs 多屏模式的设计原因：**

- **单屏模式（PROMPT_TEMPLATE_S）**：适用于功能入口页、设置页等一屏可展示完的页面
- **多屏模式（PROMPT_TEMPLATE_M）**：适用于长列表、信息流等需要滚动的页面，通过 `previous_json` 参数实现增量去重，避免重复提取已见元素

### 3.2 `qeury.py` — LLM API 调用封装

封装了对 模型服务网关 的多模态调用，支持传入图片 Base64 进行截图分析。采集阶段使用 `gemini-3.1-pro` 模型（多模态能力强）。

### 3.3 `auth_util.py` — AI Gateway 认证工具

实现 HMAC-SHA256 签名认证，遵循 模型服务网关 的安全协议。

### 3.4 `count_nodes.py` / `dedup_tree.py` — 辅助工具

- `count_nodes.py`：统计 GUI 树中的节点数量
- `dedup_tree.py`：对已采集的树进行去重清洗（处理采集过程中的重复节点）

## 四、Prompt 工程设计

采集系统的核心竞争力在于 **Prompt 的精心设计**，这直接决定了 LLM 输出的数据质量。

### 4.1 首屏 Prompt（PROMPT_TEMPLATE_S）核心规则

| 规则 | 目的 |
|------|------|
| 最短探索路径合并 | 多个元素指向同一目标时合并，避免冗余 |
| 弹窗/蒙层专注 | 有弹窗时只提取弹窗内元素，忽略底层 |
| 忽视返回按钮 | 返回操作由系统控制，不纳入知识库 |
| `is_need_to_explore` 精确控制 | 区分需要深入的入口和不需要的终态元素 |
| `action_type` 严格枚举 | 规范操作类型，便于下游处理 |

### 4.2 多屏增量 Prompt（PROMPT_TEMPLATE_M）特有规则

| 规则 | 目的 |
|------|------|
| 严格增量去重 | 参考 `previous_json`，只提取新暴露元素 |
| `滑动找到并点击` 动作类型 | 标记需要滑动才能到达的深层元素 |
| 同质化信息流限制 | 同类 feed 卡片只追加 1-2 个代表 |

### 4.3 采集数据的单节点结构

```json
{
    "uuid": "a1b2c3d4...",
    "name": "搜索框",
    "name_value": "搜索商品、品牌",
    "type": "input",
    "page_description": "商城首页",
    "function_description": "用于输入关键字来查找特定的商品或内容",
    "expected_change": "跳转至搜索中间页，弹出键盘",
    "is_need_to_explore": true,
    "action_type": "点击",
    "_explored": false,
    "children": []
}
```

## 六、设计决策与权衡

### 6.1 为什么选择 DFS 而非 BFS？

| 维度 | DFS（当前方案） | BFS |
|------|---------------|-----|
| 内存占用 | 低（只需维护当前路径） | 高（需存储整层所有节点） |
| 适合场景 | 深层功能探索 | 广度覆盖 |
| 人工操作 | 一条路走到底，操作连贯 | 频繁在不同入口间切换 |
| 断点续跑 | 天然支持（从上次停的点继续） | 复杂 |

**结论**：手机 App 的页面层级较深（3-8层），DFS 更符合实际操作习惯。

### 6.2 为什么每次操作都持久化？

采集过程中可能遇到：
- App 崩溃
- ADB 连接断开
- 手机电量耗尽
- 人工操作失误

即时持久化确保 **任何时候中断都不丢失已采集数据**。

### 6.3 为什么用多模态 LLM 而非 XML 解析？

vivo 手机的 UIAutomator XML dump 存在以下问题：
1. 许多元素缺少 `content-desc` 和 `text` 属性
2. 无法理解元素的**功能语义**
3. 动态加载的 WebView 内容无法通过 XML 获取

多模态 LLM（Gemini）直接看截图，能理解：
- 元素的视觉外观和位置
- 功能含义和交互预期
- 页面的整体上下文

## 七、已知限制

1. **采集速度**：每个节点需要截图 + LLM 调用，单个 App 约需 30-60 分钟
2. **LLM 幻觉**：偶尔会虚构不存在的界面元素（通过人工确认环节缓解）
3. **动态内容**：信息流、广告等内容每次截图可能不同
4. **弹窗干扰**：系统级弹窗（如权限申请）需要人工处理
5. **横屏/特殊状态**：部分 App 的横屏模式未覆盖
